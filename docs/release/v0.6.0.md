# tls-net v0.6.0 - Optimisation

**Measured.** v0.6.0 adds benchmarks for every performance target in the plan, an end-to-end comparison with tokio plus tokio-rustls and tokio plus tokio-openssl, and tuning on the handshake path. The API is unchanged. Results, method, and open gaps are in `docs/PERFORMANCE.md`.

## Results

- **Against rustls alone.** Built from the same rustls configurations and driven the same way, a tls-net handshake costs 2.2% more on Linux and 0.7% more on Windows (target: within 3%). A received record costs 32 ns more, or one extra copy at 16 KiB until rustls 0.24's in-place reads. A sent record costs about 10 ns more. tls-net's code makes no allocation per record.
- **Memory.** An idle connection holds 257 bytes beyond rustls's own state.
- **End to end on net-io's reactor**, interleaved with the other stacks on the same 8 cores:
  - Bulk transfer runs at 1.23 times tokio-rustls's rate with 17% less CPU per byte.
  - Handshakes run at 1.45 times the rate, at about the same CPU per handshake.
- **The parts tls-net owns:** ClientHello parse plus JA4 in 0.82 µs, SNI lookup among 10,000 names in 75 to 101 ns, a reload of 100 certificates in 1.74 ms, ticket seal and open in 1.6 and 1.5 µs.

## Changed

- An idle server session keeps its SNI and peer identity on the heap (656 bytes over rustls before, 257 now).
- Ticket sealing makes one allocation and takes the key ring's lock once.
- `accept` takes the handshake slot without cloning a reference.
- The peer identity is built when first read instead of at every handshake.

## Open

Two end-to-end targets are not met yet, and both gaps are in net-io's reactor:

- **CPU per handshake** should be at least 20% below tokio-rustls's. Fewer sends per connection and accepting on the worker are scheduled for net-io 0.8.
- **Idle memory** should be at least 30% below tokio-rustls's. net-io 0.6 keeps two 64 KiB buffers per TLS connection, which also limits a default reactor to 4,096 TLS connections.

Both are part of the 1.0 gate.
