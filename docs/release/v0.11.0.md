# tls-net v0.11.0 - QUIC

**QUIC handshakes and packet keys, behind the new `quic` feature.** tls-net now runs the TLS side of a QUIC connection (RFC 9001) and hands out the keys that protect its packets. The transport, quic-net for example, frames CRYPTO data and sends packets; tls-net does no I/O and puts no rustls type in its API. Nothing changes for a build without the feature.

## Added

- **`TlsServer::accept_quic` and `TlsClient::connect_quic`** return a `QuicSession`. Feed it the CRYPTO data that arrives, one encryption level per call, take what to send, and install the keys each `KeyChange` hands out:

  ```rust,ignore
  let mut session = server.accept_quic(transport_params)?;
  session.read_handshake(&crypto_data)?;
  let mut out = Vec::new();
  if let Some(KeyChange::Handshake { keys }) = session.write_handshake(&mut out) {
      // send `out` at the current level, then switch to `keys`
  }
  ```

  `WorkerAcceptor::accept_quic` and `TlsClient::connect_quic_to` (for a pinned identity) work the same way.
- **The same checks as TCP.** A QUIC ClientHello goes through the hello parser and its budgets, the hello hook, the SNI table and host groups, the handshake budget, the capacity cap, and the checks at completion. A host policy's client certificate and ALPN hold over QUIC, and `host_scope(session.server_name())` gives the `Host` check. JA4 starts with `q` for a hello that came over QUIC, and `ClientHelloView::is_quic` tells the hook.
- **Keys.** `PacketKey::seal` and `open`, the AEAD limits, `HeaderKey::mask`, and `Secrets::next_packet_keys` for key updates.
- **No session needed.** `quic::initial_keys` derives the Initial keys from the client's first connection ID, and `quic::retry_tag` computes the Retry Integrity Tag.
- **`TlsError::QuicInput`** (`TLS-0048`): a connection ID over 20 bytes, or a payload longer than the AEAD allows.

## Behaviour to know

- QUIC needs TLS 1.3 and an ALPN protocol. `accept_quic` and `connect_quic` refuse a configuration without them; on a server, every host group needs both. A policy that also allows TLS 1.2 is fine: QUIC connections only ever use TLS 1.3, and tls-net checks that again when the handshake ends.
- A failed session stays failed. Close the connection with `CRYPTO_ERROR` (`0x100 + alert()`). A hello tls-net cannot read, the hello hook, and the budgets have no alert, as over TCP.
- A server must not process 1-RTT packets until `is_handshaking()` is `false`.

## Tests

- RFC 9001 appendix A byte for byte: the client and server Initial packets, the Retry tag, and the ChaCha20 key schedule with its key update.
- A client and a server in memory, to 1-RTT keys and two key updates, with CRYPTO data whole and one byte at a time; resumption.
- The refusals and their alerts, and every check a TCP accept has, over QUIC.
- Both providers, aws-lc-rs and ring.

## Costs

The QUIC handshake costs what a TCP accept does on top of rustls: the hello parse, JA4, and the SNI lookup. Against rustls's own QUIC connection, in memory on Linux: full handshake 1.3% over, resumed 1.4%; sealing, masking, and opening an Initial packet cost the same as rustls (ratio 1.00). The ClientHello is copied once while it is buffered. The TCP paths did not move (full handshake 1.014 to 1.013 of rustls, resumed 1.010 to 1.010).

## Fuzzing

Three new targets: `quic_hello_parse`, `quic_step_server`, and `quic_step_client`, seeded from real handshakes.

## Upgrading from 0.10

Nothing to change. To use QUIC, turn on the `quic` feature.
